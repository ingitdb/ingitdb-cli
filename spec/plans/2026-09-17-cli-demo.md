# Plan: `ingitdb demo` with the TODO demo shared with OpenVaultDB

**Status:** Draft
**Source Feature:** cli/demo
**Date:** 2026-09-17
**Owner:** alex
**Supersedes:** —

## Summary

Delivers `ingitdb demo install` across three repositories: the TODO demo records move into a
new standard-library-only package in `ingitdb-go`, OpenVaultDB's `ovdb` switches its built-in
demo to that package with no behaviour change, and `ingitdb-cli` gains
`select --from=<collection>/<record>/<subcollection>` with terminal UI drill-down (without
which the demo's items cannot be queried or browsed) and then the `demo` command. Releases
land provider first. Every acceptance criterion of `cli/demo` is covered; none is deferred.

## Approach

**Why the records live in `github.com/ingitdb/ingitdb-go/ingitdb` (package `demos/todo`).**
It is the lowest module both consumers already have in their module graph: `ingitdb-cli`
requires it directly and `ovdb` indirectly (through `openvaultdb-go` and `dalgo2ingitdb`). It
depends on neither consumer, so no cycle is possible. The package imports only the Go
standard library and holds only what both consumers use (`App`, `Lists`, `Records`), so `ovdb`
takes on no inGitDB engine API. `dalgo2ingitdb` was rejected (a storage driver is the wrong
owner for seed content), `openvaultdb-go` because inGitDB must not depend on OpenVaultDB,
and a new module because it adds a release train for about a hundred lines of data. No
separate feature spec in `ingitdb-go`: the contract is `cli/demo#REQ:shared-demo-data` plus
OpenVaultDB's `todo-demo#REQ:seed-from-shared-package`.

**Titles are demo data, not UI copy.** The list and item titles are English records owned by
the shared package. `ovdb` reads them from the package and drops its `demo.seed.*` copy keys;
OpenVaultDB's copy-catalogue rule covers user-interface strings, not seed records, and both
specs say so.

**Explicit definitions in `ingitdb-cli`, not schemaless.** On disk every inGitDB collection
needs a definition: OVDB's "schemaless" mode means OVDB infers and writes definitions on first
write. `ingitdb-cli` has no inference and its `validate`, `select` and terminal UI read
definitions, so the command writes explicit definitions for `lists` and its subcollection
`items`. They and the `.ingitdb/demo.yaml` marker have one consumer, so they live in
`ingitdb-cli`. `ovdb` keeps its schemaless registration, so its demo files do not change; the
two installs share records, not definition files. OVDB's inferred definitions declare the
advisory `id` column non-nullable, which `dalgo2ingitdb` writes as `required: true`, so every
schemaless OVDB inGitDB database, OVDB's demo included, fails `ingitdb validate`. That is a
known OVDB defect fixed separately in
[openvaultdb-go#25](https://github.com/openvaultdb/openvaultdb-go/issues/25), not in this
stream. A second known limitation of OVDB's demo folder, also not fixed here: after
`ovdb demo install`, `git status` in the folder is not clean, because driver commits use a
temporary index and never update `.git/index` and do not include definition files
([dalgo2ingitdb#12](https://github.com/ingitdb/dalgo2ingitdb/issues/12)).

**Subcollection addressing for `select --from` and the terminal UI comes first.** The demo
nests items under lists (OpenVaultDB decision 0010 declined a flat layout). Today
`select --from` and the terminal UI only reach root collections; verified 2026-09-17:
`select --from=lists` works, `select --from=lists/to-buy/items` fails with
`collection "lists/to-buy/items" not found in definition`. Because a `/` in `--from` is
always an error today, adding it breaks nothing. `--id` is not changed: `id-flag-format`
stays as it is and subcollection `--id` addressing is left as an open question in the new
spec.

**Git.** `dalgo2ingitdb` commits record paths into whatever work tree contains the database,
which would be the enclosing repository when `todo-demo` sits inside one. The command
therefore runs `git init` before any write, writes through `dalgo2ingitdb4local` (which does
not commit), and makes the single install commit itself.

**Validation evidence.** `ingitdb validate` does not check subcollection records today (a bad
item record still reports `All 2 records are valid`). Item validity is therefore proved by a
test that runs `datavalidator` on every record against the definitions the command writes; the
`validate` gap is a separate issue, not widened into this stream.

## Tasks

### Task 1: Shared TODO demo records in ingitdb-go

**Verifies:** cli/demo#ac:fresh-install

Repository `ingitdb/ingitdb-go`, module `ingitdb`. Add package `ingitdb/demos/todo`,
standard-library imports only:

- `App = "todo"` and `Lists` (`lists/to-buy`, `lists/to-watch`, in display order).
- `Records(now time.Time) []Record`, `Record{Key string; Data map[string]any}`, keys without a
  leading slash, each list record before its items, English titles and ids exactly as `ovdb`
  seeds today (To buy: Milk, Bananas, Coffee; To watch: The Matrix, Interstellar),
  `done: false`, and `added_at` one second apart ending at `now` truncated to the second, UTC,
  RFC 3339.

Tests: golden test pinning every record at a fixed `now` (the values `ovdb`'s `demo_test.go`
expects today); a test that the package imports only the standard library; 100% statement
coverage. Release: tag `ingitdb/v0.7.0`.

### Task 2: ovdb seeds from the shared package, no behaviour change

**Verifies:** cli/demo#ac:fresh-install

Repository `openvaultdb/ovdb`, after Task 1's tag and after increment 5 lands (it edits the
same package). Require `github.com/ingitdb/ingitdb-go/ingitdb v0.7.0`; replace the literals and
`uicopy.T("demo.seed.*")` calls in `internal/setup/demo.(*Service).seed` with
`todo.Records(now)` mapped to `Op` (`Path: "/" + Key`), and derive `demo.Lists` from the shared
`Lists` with a leading slash. Remove the `demo.seed.*` keys from `copy/en.json` (confirm the web
build and the copy tests do not reference them). Nothing else changes: schemaless
registration, `demos.json`, reconnect, refusal copy and Journey D are untouched.

Proof of no behaviour change (verifies OpenVaultDB `todo-demo#AC:seed-from-shared-package`):
the existing `internal/setup/demo` and local-server demo tests pass unmodified, plus a test
asserting the seeded records sent to the data API are byte-identical to a golden batch
captured from `main` before editing. Run the full `ovdb` suite, since the `ingitdb-go` bump
also reaches `openvaultdb-go` and `dalgo2ingitdb` through minimal version selection.

### Task 3: `select --from` subcollection paths and terminal UI drill-down

**Verifies:** cli/demo#ac:select-lists-and-items, cli/demo#ac:tui-shows-items

Repository `ingitdb/ingitdb-cli`. First write and review a short feature spec
(`spec/features/subcollection-addressing`) limited to: `select --from=<collection>/<record>/<subcollection>`
(repeatable to deeper levels), where each odd segment after the root must be a subcollection
the parent definition declares, otherwise the existing "not found" error; set-mode flags
(`--where`, `--order-by`, `--fields`, `--limit`, `--format`) behave as for a root collection;
and terminal UI drill-down from a record into a declared subcollection's records and back
with Esc. Out of scope, recorded as open questions there: `--id` addressing of subcollection
records (no `id-flag-format` change), `describe`, `list collections`, write verbs and
`--remote`. Record paths resolve through the local driver's parent-chain scoping
(`resolveScopedCollection`), so on-disk layout stays the driver's.

Tests: `select --from` on a nested fixture in every format, an undeclared subcollection
segment, and a root `--from` unchanged; terminal UI model tests for opening and leaving a
subcollection.

### Task 4: `ingitdb demo install` command

**Verifies:** cli/demo#ac:fresh-install, cli/demo#ac:install-at-path, cli/demo#ac:reinstall-keeps-edits, cli/demo#ac:non-empty-folder-refused, cli/demo#ac:file-target-refused, cli/demo#ac:empty-folder-used, cli/demo#ac:failure-leaves-nothing, cli/demo#ac:no-prompt-without-terminal, cli/demo#ac:one-commit-own-repository, cli/demo#ac:without-git, cli/demo#ac:json-output, cli/demo#ac:next-steps-in-order, cli/demo#ac:plain-ingitdb-folder

Repository `ingitdb/ingitdb-cli`, after Tasks 1 and 3. Files in `cmd/ingitdb/commands/`:
`demo.go` (cobra `demo` group and `install`), `demo_schema.go` (the `lists` and `items`
`ingitdb.CollectionDef` values: `{key}.yaml` single-record files; `lists.title` string
required; `items.title` string required, `items.done` bool, `items.added_at` `datetime`;
`columns_order: [title, done, added_at]`; no `id` column; and the `.ingitdb/demo.yaml`
marker type with `app` and `version: 1`), `demo_install.go` (target checks, write, git,
cleanup), `demo_output.go` (text and `--format=yaml|json`), tests beside them, and
registration in `cmd/ingitdb/main.go`.

Order of operations: resolve and check the target (file, non-empty without marker, another
demo's marker, TODO marker means already installed); create the folder or accept an empty
one; `git init` when `git` is on `PATH`; write `.ingitdb/settings.yaml`,
`.ingitdb/root-collections.yaml`, the definitions and the marker; write the records from
`todo.Records(time.Now())` through `dalgo2ingitdb4local`. If that driver cannot write nested
keys at the same paths `dalgo2ingitdb` uses, fix it there; never accept a second on-disk
layout, and never write before `git init` to dodge driver commits. Then `git add -A` and one
commit `Install the TODO demo`, setting `GIT_AUTHOR_NAME`/`GIT_COMMITTER_NAME` to `inGitDB`
only when `git config user.name` is empty in the folder and `GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_EMAIL`
to `ingitdb@localhost` only when `git config user.email` is empty. On any failure remove what
was written. List paths in output and next steps come from `todo.Lists`.

Test details: seams for the failure test (a writer failing on the fourth record) and for a
`PATH` without `git`; git tests isolated with `GIT_CONFIG_GLOBAL` set to an empty file,
`GIT_CONFIG_NOSYSTEM=1` and a temporary `HOME`, because the VM and CI runners have a global
identity that would hide the fallback; a `datavalidator` test over every root and item
record against `demo_schema.go`'s definitions (item validity, which `validate` does not
check); path quoting with double quotes on Windows and POSIX single quotes elsewhere, each
tested by running the printed command through the platform shell; printed absolute paths
compared after `filepath.EvalSymlinks` (macOS `/var` is a link to `/private/var`). Every
branch covered; `golangci-lint run` clean.

### Task 5: Cross-platform CI

**Verifies:** cli/demo#ac:works-on-every-os

Add a workflow job running the demo, `select` and terminal UI tests on `ubuntu-latest`,
`macos-latest` and `windows-latest`, scoped to those packages to keep CI cost down. The
OpenVaultDB connect behaviour is verified in the `ovdb` repository against OpenVaultDB's own
AC `ingitdb-demo-folder-not-adopted` (working tree, index and `HEAD` unchanged; connect may
add lock files under `.git`), not by this repository's CI.

### Task 6: Documentation

**Verifies:** cli/demo#ac:next-steps-in-order

`docs/cli/commands/demo.md` (synopsis, flags, output, next steps) and a link from

`spec/features/README.md`; add `// specscore: feature/cli/demo` annotations and fill the

`modules/todo` (tasks, statuses, tags) is a schema example, not the TODO demo.

### Task 7: Release order

**Verifies:** cli/demo#ac:fresh-install

1. `ingitdb-go`: merge Task 1, tag `ingitdb/v0.7.0`.
2. In parallel: `ovdb` pull request for Task 2; `ingitdb-cli` pull requests for Task 3, then
   Tasks 4 to 6 (bump `ingitdb-go` in the first).
3. Release `ingitdb-cli` from `main`; the existing release workflow publishes Homebrew, Snap,
   WinGet, Chocolatey and Scoop packages, so no packaging change is needed. Task 3 ships in
   the same release as Task 4 or an earlier one, so no printed step fails.
4. Release `ovdb` with Task 2 on its normal train (independent of step 3).
5. At the end of the stream, converge the fleet on `ingitdb-go` v0.7.0 with
   `wb deps propagate`: `dalgo2ingitdb`, `dalgo2ingitdb4local` (still on ingitdb-go v0.5.2)
   and `openvaultdb-go`; no functional change there.
