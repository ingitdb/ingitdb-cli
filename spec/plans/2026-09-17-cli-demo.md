# Plan: `ingitdb demo` with the TODO demo shared with OpenVaultDB

**Status:** Draft
**Source Feature:** cli/demo
**Date:** 2026-09-17
**Owner:** alex
**Supersedes:** —

## Summary

Delivers `ingitdb demo install` across four repositories: the TODO demo data moves into a
new package in `ingitdb-go`, OpenVaultDB's `ovdb` switches its built-in demo to that package
with no behaviour change, `ingitdb-cli` gains subcollection addressing (without which the
demo's items cannot be queried or browsed) and then the `demo` command, and the releases land
provider first. Every acceptance criterion of `cli/demo` is covered; none is deferred.

## Approach

**Why the data lives in `github.com/ingitdb/ingitdb-go/ingitdb` (package `demos/todo`).**
It is the lowest module both consumers already use: `ingitdb-cli` requires it directly and
`ovdb` indirectly (through `openvaultdb-go` and `dalgo2ingitdb`). It depends on neither
consumer, so no cycle is possible, and the demo's collection definitions are
`ingitdb.CollectionDef` values from that same module. `dalgo2ingitdb` was rejected (a
storage driver is the wrong owner for seed content, and `ovdb` does not import it directly);
`openvaultdb-go` was rejected because inGitDB must not depend on OpenVaultDB; a new module
was rejected because it adds a release train for about a hundred lines of data. The package
holds data only (records, definitions, marker); writing stays with each consumer, because
`ovdb` seeds through its data API and `ingitdb-cli` through its driver.

**Schema, not schemaless.** On disk every inGitDB collection needs a definition: OVDB's
"schemaless" mode only means OVDB infers and writes definitions on first write (an `id`
column plus inferred fields). `ingitdb-cli` has no inference and its `validate`, `select`
and terminal UI read definitions, so the shared package ships explicit definitions for
`lists` and its subcollection `items` (titles, column types, `columns_order`) that make
`ingitdb validate` pass. `ovdb` keeps its schemaless registration and inference, so its demo
files do not change; the two installs share records, not definition files.

**Subcollection addressing comes first.** The demo nests items under lists (OpenVaultDB
decision 0010 declined a flat layout). Today `select --from` and the terminal UI only reach
root collections (`describe` lists subcollections as out of scope pending an addressing
convention); verified on 2026-09-17 against a hand-built fixture: `select --from=lists`
works, `select --from=lists/to-buy/items` fails with `collection "lists/to-buy/items" not
found in definition`. Task 3 specifies and builds the convention before the demo command.

**Git.** `dalgo2ingitdb` commits record paths into whatever work tree contains the database,
which would be the enclosing repository when `todo-demo` sits inside one, and it does not
commit definition files. The command therefore runs `git init` before any write, writes
without driver commits, and makes the single install commit itself.

## Tasks

### Task 1: Shared TODO demo data package in ingitdb-go

**Verifies:** cli/demo#ac:fresh-install

Repository `ingitdb/ingitdb-go`, module `ingitdb`. First add a SpecScore feature there
(`spec/features/todo-demo-data`) and take it through that repository's review gate. Then add
package `ingitdb/demos/todo` with:

- `App = "todo"` and `Lists` (`lists/to-buy`, `lists/to-watch`, in display order).
- `Records(now time.Time) []Record`, `Record{Key string; Data map[string]any}`, keys without a
  leading slash, list record before its items, titles and ids exactly as `ovdb` seeds today
  (To buy: Milk, Bananas, Coffee; To watch: The Matrix, Interstellar), `done: false`, and
  `added_at` one second apart ending at `now` truncated to the second, UTC, RFC 3339.
- `Definition() *ingitdb.CollectionDef` for root collection `lists` (with `items` in
  `SubCollections`), `{key}.yaml` single-record files, `title` required; `items` with `title`
  (required), `done` (bool), `added_at` (use `datetime` only if the record validator accepts
  RFC 3339 strings, otherwise `string`), `columns_order: [title, done, added_at]`, and no
  required `id` column (OVDB's inferred `id` column is required and fails `ingitdb validate`
  on records that do not store it).
- `Marker` type and file name for `.ingitdb/demo.yaml` (`app`, `version: 1`); confirm the
  root-config reader and `validate` ignore the file.

Tests: golden test pinning every record at a fixed `now` (the same values `ovdb`'s
`demo_test.go` expects today); definitions load through the definition validator from a
temporary folder; every seed record passes column validation against them; 100% statement
coverage of the package. Release: tag `ingitdb/v0.7.0`.

### Task 2: ovdb seeds from the shared package, no behaviour change

**Verifies:** cli/demo#ac:fresh-install

Repository `openvaultdb/ovdb`, after Task 1's tag and after increment 5 lands (it edits the
same package). Require `github.com/ingitdb/ingitdb-go/ingitdb v0.7.0` directly; replace the
literals in `internal/setup/demo.(*Service).seed` with `todo.Records(now)` mapped to `Op`
(`Path: "/" + Key`), and `demo.Lists` with the shared `Lists` given a leading slash. Remove
the `demo.seed.*` keys from `copy/en.json` (Go-only today; confirm the web build and the copy
tests do not reference them). No other change: registration stays schemaless, `demos.json`,
reconnect, refusal copy and Journey D are untouched.

Proof of no behaviour change: the existing `internal/setup/demo` and local-server demo tests
pass unmodified, plus one added test asserting the batch sent to the data API is byte-identical
to the one produced before the switch (captured as a golden file from `main` before editing).
Run the full `ovdb` suite, since the `ingitdb-go` bump also reaches `openvaultdb-go` and
`dalgo2ingitdb` through minimal version selection.

### Task 3: Subcollection addressing for select and the terminal UI

**Verifies:** cli/demo#ac:select-lists-and-items, cli/demo#ac:tui-shows-items

Repository `ingitdb/ingitdb-cli`. First write and review a feature spec
(`spec/features/subcollection-addressing`), amending `id-flag-format` and
`shared-cli-flags`. Proposed convention, to be confirmed in that review: a path alternates
collection and record ids from a root collection (`lists/to-buy/items`, and
`--id=lists/to-buy/items/milk`); a segment is read as a subcollection only when the parent
collection's definition declares a subcollection with that name, so every existing root
`--id` whose key contains `/` keeps its meaning. Record paths resolve through
`dalgo2ingitdb`'s parent-chain scoping (`resolveScopedCollection`), so on-disk layout is the
driver's. Terminal UI: from a record of a collection with subcollections, open a
subcollection's records screen (reuse the collection screen with a scoped definition) and
return with Esc. `list collections` and `describe` stay root-only unless the review widens
scope.

Tests: `select` set and single-record modes on a nested fixture, including a root collection
whose keys contain `/`; terminal UI model tests for opening and leaving a subcollection.

Repository `ingitdb/ingitdb-cli`, after Tasks 1 and 3. Files: `cmd/ingitdb/commands/demo.go`
(cobra `demo` group and `install`), `demo_install.go` (target checks, write, git, cleanup),
`demo_output.go` (human text and `--format=yaml|json` document), tests beside them, and
registration in `cmd/ingitdb/main.go`. Order of operations: resolve and check the target
(file, non-empty without marker, other demo's marker, TODO marker means already installed);
create the folder or accept an empty one; `git init` when `git` is on `PATH`; write
`.ingitdb/settings.yaml`, `.ingitdb/root-collections.yaml`, the definitions from
`todo.Definition()` and the marker; write records from `todo.Records(time.Now())` through the
local driver (`dalgo2ingitdb4local`, which does not commit). If that driver cannot write
nested keys at `dalgo2ingitdb`'s paths, fix it there or add a no-commit option to
`dalgo2ingitdb`; never accept a second on-disk layout, and never write before `git init`
to dodge driver commits; `git add -A` and
one commit `Install the TODO demo`, passing `GIT_AUTHOR_*`/`GIT_COMMITTER_*` as
`inGitDB <ingitdb@localhost>` only when `git config user.email` is empty in the folder; on any
failure remove what was written. Seams for the failure test (inject a writer that fails on
the fourth record) and for a `PATH` without `git`. Quote paths in next steps with
PowerShell-safe quoting on Windows and POSIX quoting elsewhere. Every exported path and every
branch covered by tests; `golangci-lint run` clean.

### Task 7: Release order

**Verifies:** cli/demo#ac:fresh-install

1. `ingitdb-go`: merge Task 1, tag `ingitdb/v0.7.0`.
2. In parallel: `ovdb` pull request for Task 2; `ingitdb-cli` pull requests for Tasks 3, then
   4 to 6 (bump `ingitdb-go` in the first).
3. Release `ingitdb-cli` from `main`; the existing release workflow publishes Homebrew, Snap,
   WinGet, Chocolatey and Scoop packages, so no packaging change is needed. Do not release
   Task 3 alone with a printed step that fails: Tasks 3 and 4 ship in the same release or 3
   first.
4. Release `ovdb` with Task 2 on its normal train (independent of step 3).
5. At the end of the stream, bump `ingitdb-go` in `dalgo2ingitdb` and `openvaultdb-go` so the
   fleet converges on one version; no functional change there.
